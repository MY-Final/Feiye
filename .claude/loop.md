# 扉页 · 自动化产品迭代循环

本仓库是「扉页」：Tauri 2 + React + CodeMirror 6 的本地优先 Markdown 编辑器。
一轮 = 1 条需求，由四个角色接力完成：用户 → 产品 → 开发 → 测试。
节奏：2–3 分钟一轮；每完成 5 条需求，下一轮做检验轮；时间窗由 `docs/loop/state.md` 顶部记录。

## 0. 恢复上下文（每轮必做）

1. `git status`：工作区不干净先弄清是谁的改动，绝不覆盖用户未提交的改动。
2. 读 `docs/loop/state.md`：轮次、时间窗、自上次检验轮的计数。
3. 读 `docs/loop/backlog.md` 顶部几条：最近做过什么、什么被延后。
4. 读 `README.md` 的「设计原则」「功能规划」：那是产品边界；**不碰「暂不做」**。

## 1. 用户

以一位真实用户的口吻，提出 **1 条**具体、可验证的需求或抱怨（新功能，或已有功能的优化）。

- 与 backlog 已有条目不重复（换个角度也算重复）。
- 从「计划中 / 后续」里用户真正会碰到的痛点，或已实现功能的粗糙处出发。
- 格式：「场景 → 现在的问题 → 期望的结果」，不超过 5 行。

## 2. 产品

- 是否契合「本地优先、纯文本、快、安静、数据安全」的设计原则；
- 在「暂不做」边界内吗；是否扩大了产品边界；
- 价值 vs 成本；结论：**做 / 不做 / 延后** + 一句理由。

## 3. 开发

- **前端**：涉及 `src/` 哪些模块；交互与状态风险；工作量 S/M。
- **后端**：涉及 `src-tauri/` 哪些命令或文件系统行为；数据安全与原子写入；工作量 S/M。
- 裁决：产品结论为「做」，且前后端工作量都是 S（≤ 约 80 行、≤ 3 个文件）才做；否则只记录结论，不改代码。

## 4. 测试

- 自动化：前端 `$HOME/.bun/bin/bun run build`（含 tsc）；改了 `src-tauri/` 跑 `(cd src-tauri && cargo test)`。
- 能在运行中的应用里点到的，用 CDP（端口 9222）真实交互验证；工作区 `D:\clawWorkSpeace\新建文件夹`。
- 没法自动化的，在 backlog 里留下人工可复现步骤：改了哪、怎么点、预期什么。

## 5. 记录与提交

- 在 `docs/loop/backlog.md` 最上方按文件头模板追加本轮记录（含测试步骤）。
- 更新 `docs/loop/state.md`：轮次、最后更新、一行进展；裁决为「做」时把「自上次检验轮」计数 +1。
- 提交：`feat|fix|perf(scope): 中文描述`，只提交本轮相关文件。

## 6. 检验轮

`state.md` 里「自上次检验轮」计数满 5 时，本轮改为检验轮：不实现新功能，系统性回归上一批 5 条改动——构建 + 后端测试 + 用 CDP 实际操作关键路径；发现问题直接修或记为下一轮需求，在 backlog 写「检验轮」记录，并把计数清零。

## 7. 终止条件

系统时间到 `state.md` 记录的窗口终点，或 `docs/loop/roadmap.md` 的条目全部完成为止（当前窗口不设固定终点，以路线图完成为准）：

1. 在 `state.md` 写本窗口小结，状态改为「已结束」；
2. 用 CronList 找到本循环的定时任务并 CronDelete；
3. 提交后向用户汇报：做了几轮、主要成果、已知遗留。

## 硬性约束

- 不 push、不创建 PR、不改 README 中已承诺的产品边界。
- 不新增依赖、不改构建配置。
- 每轮只做 1 条需求，宁可少做，不要批量重构。
- 分支 `loop/optimize`（优化窗口，从 `main` 新建）；bun 一律用 `$HOME/.bun/bin/bun`。
- 每轮控制在 2–3 分钟内完成；做不完就把它拆小。
