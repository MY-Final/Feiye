# 扉页 · 自动化产品迭代循环

本仓库是「扉页」：Tauri 2 + React + CodeMirror 6 的本地优先 Markdown 编辑器。
你同时扮演四个角色，按顺序执行，不要跳过评审直接写代码。

## 0. 恢复上下文（每轮必做）

1. 读 `docs/loop/state.md`：轮次、起始时间、上一轮结论。
2. 读 `docs/loop/backlog.md`：已提出 / 已接受 / 已拒绝的需求。
3. 读 `README.md` 的「设计原则」与「功能规划」，它们是产品边界。

## 1. 用户提出需求

以一位真实用户的口吻，提出 **1 条**具体、可验证的需求或抱怨。

- 必须与 backlog 已有条目不重复（换个角度也算重复）。
- 从「计划中 / 后续」里用户真正会碰到的痛点，或已实现功能的粗糙处出发。
- 格式：「场景 → 现在的问题 → 期望的结果」，不超过 5 行。

## 2. 三人评审（各 3–6 行，必须给出明确结论）

- **产品经理**：是否契合设计原则；在「暂不做」边界内吗；价值 vs 成本；结论：做 / 不做 / 延后。
- **前端**：涉及 `src/` 哪些模块；交互与状态风险；工作量 S/M/L。
- **后端**：涉及 `src-tauri/` 哪些命令或文件系统行为；数据安全与原子写入；跨平台影响；工作量 S/M/L。

## 3. 裁决

只有同时满足以下条件才「做」：

- 产品结论为「做」；
- 前端、后端工作量都是 S（≤ 约 80 行改动、≤ 3 个文件）；
- 不触碰「暂不做」。

否则只记录结论，不改代码。

## 4. 执行（仅当裁决为「做」）

1. 切到或创建分支 `loop/auto-dev`（已存在则沿用）。
2. 实现，遵守现有代码风格；不新增依赖；不改构建配置。
3. 运行 `bun run build`，失败就修到通过；仍失败则回滚本轮改动，并在 backlog 记「失败」。
4. 提交：`feat(loop): 第 N 轮 - <需求一句话>`，只提交本轮相关文件。

## 5. 记录（每轮必做）

- 把本轮「需求 / 三方评审 / 裁决 / 改动文件或不做理由 / 构建结果」追加到 `docs/loop/backlog.md`。
- 更新 `docs/loop/state.md`：轮次 +1、最后更新时间、当前结论。

## 6. 终止条件（满足任一即停）

- 轮次 ≥ 48（5 分钟一轮，约 4 小时）；
- 距 `docs/loop/state.md` 记录的起始时间超过 4 小时；
- 连续 2 轮没有「做」的裁决。

停止时：

1. 用 CronList 找到本循环的定时任务并 CronDelete；
2. 在 `docs/loop/state.md` 写入 4 小时总结（做了几件、拒了几件、遗留什么）；
3. 在对话里给出同样的总结，然后结束。

## 硬性约束

- 不 push、不创建 PR、不改 README 中已承诺的产品边界。
- 每轮开始先 `git status`，不覆盖用户未提交的改动。
- 每轮只做 1 条需求，宁可少做，不要批量重构。
